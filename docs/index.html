Why "enrollment-weighted": the raw row grain is one row per course-offering-instructor. An unweighted majority-class baseline came out to 75.8% — inflated, because a 3-student independent-study section (almost always an A) counts the same as a 300-student lecture. Weighting by actual enrollment (78.8%) is the honest number, and both the baseline and XGBoost training use it.

Pipeline

Madgrades and RateMyProfessor feed date-versioned raw data into GCS, which flows through BigQuery into a feature table and a tuned, tracked model — with a scheduled job keeping it all current.

  1. 1
    Ingest
    Pull course/grade data from Madgrades' REST API and instructor ratings from RateMyProfessor's GraphQL endpoint.
  2. 2
    Version
    Write raw JSON to GCS under a date-stamped prefix — every pull is kept, nothing is overwritten.
  3. 3
    Transform
    Flatten section-level grade distributions, fuzzy-match instructor names across the two sources (no shared ID), load clean tables into BigQuery.
  4. 4
    Train
    Build the enrollment-weighted feature table, tune XGBoost with Optuna, track every run and register the best model in MLflow.
  5. 5
    Automate
    A Dockerized Cloud Run Job, triggered weekly by Cloud Scheduler, reruns the whole pipeline so the dataset stays current.
Full source, commit history, and every real bug found while building this (API field-name mismatches, a case-sensitivity bug in the instructor fuzzy-matcher, a Cloud Run OOM, etc.) are on github.com/RithikGobinath/CourseIQ.
